# 飞书机器人菜单「单入口 → 代码控制菜单卡」方案可行性

- 类型:**调研结论**(纯调研 · 供产品负责人定方案 · 不改代码)
- 日期:2026-05-30
- 关联:ADR 0032 · `docs/research/feishu-polish-research.md` · `docs/research/feishu-bot-menu-setup.md`(静态多项方案 A)
- 背景:产品设想 —— 飞书左下角只配 **1 个固定入口**(如「菜单」),点击后弹出的菜单内容
  (行情 / 持仓 / 下单)由**代码控制**(我们已有 `build_main_menu`),而非在飞书后台一项项配死。
  好处:改菜单(增项 / 改名 / 调序)都在代码里改,飞书后台只设置一次。

## 结论速览
✅ **完全可行,且我们代码零改动**(`menu_v6` 分支 + `build_main_menu` + `card.action.trigger` 都已在 prod)。
飞书后台只需配 **1 个菜单项**,响应动作选「推送事件」,event_key 填 **`menu:main`**。
点击 → 飞书推 `application.bot.menu_v6` 事件 → 我们 server 主动发主菜单卡 → 用户点卡按钮逐级展开。
★ 这条链成立的前提是「**自建应用**」(我们正是),不是简单的「自定义机器人(webhook bot)」。

## Q1:支持「单入口 → 事件 → 返回交互菜单卡 → 逐级展开」吗?→ **YES**
逐环节(官方文档 + 我们现成代码):
1. 菜单项可选「推送事件」动作,event_key 是**开发者任意自定义的字符串**(原文:"自定义用户点击菜单
   事件的唯一标识…作为机器人自定义菜单事件回调中 event_key 的值发送给你的服务器")→ 填 `menu:main` 没问题。
2. 用户点击 → 飞书**只推一个事件** `application.bot.menu_v6`(区别于 `im.message.receive_v1`),**不自带展开**;
   原文:"接收到用户的点击事件后,你可以通过服务端 OpenAPI 调用的方式响应用户操作" → **由我们 server 决定回什么**(主动发卡)。
3. 我们的 `menu_v6` 分支已把 event_key 当 action 路由进 `handle_inbound`;`menu:main` 已 `return build_main_menu`;
   `render_for_feishu` 已渲染主菜单卡 → **点菜单 ≡ 触发 menu:main ≡ 弹主菜单卡**。
4. 卡片按钮(行情 / 持仓 / 下单)走 `card.action.trigger` **原地刷新逐级展开** —— 自建应用能力(见 ★)。

## ★ 关键前提:我们是「自建应用」,不是「自定义机器人」
飞书官方区分两类,卡片回调能力不同:
- **自定义机器人(custom bot · 一个 webhook 地址)**:发的卡片**只支持按钮 / 文字链跳 url,不支持点击回调到服务端** → 做不了"卡片按钮逐级展开"。
- **自建应用(企业自建应用 · App ID/Secret + 事件订阅)**:**支持 `card.action.trigger` 回调** → 卡片按钮能逐级展开。

我们用的就是**自建应用**(ADR 0032 · App ID/Secret/事件订阅齐全 · `card.action.trigger` 原地刷新已在 prod 跑通)→ **设想成立**。

## Q2:怎么配 + 代码要不要调
**飞书后台(产品负责人 / 管理员 · 无代码):**
1. 开发者后台 → 应用 → 机器人 → 机器人自定义菜单 → 开启。
2. 配 **1 个主菜单项**:文案「📋 菜单」(随意),响应动作选「**推送事件**」,event_key 填 **`menu:main`**。
3. 确认订阅「机器人自定义菜单事件」(`application.bot.menu_v6`),回调地址同现有 webhook。
4. 创建版本 → 发布 → 等 ~5 分钟生效。

**代码侧:零改动。** `menu_v6 → handle_inbound → build_main_menu → render_for_feishu` + `card.action.trigger` 全部就绪。配个 `menu:main` 就弹主菜单卡。
(可选小优化:`render_main_menu` 主菜单文案老旧 · 待办 #295 · **不阻塞**本方案。)

## Q3:限制 + 形态差异(诚实说清)
- 飞书原生菜单**没有**"点菜单项就地弹出一个浮层卡片"的能力 —— 它只能「推事件」,卡片是我们 server
  **主动发到会话里的一条新消息**。所以体验是:点左下角「📋 菜单」→ **会话里出现一张主菜单卡** → 点卡上的按钮逐级展开。
- 这跟"菜单悬浮层里直接展开选项"略有**形态差异**(卡片是 IM 消息、不是菜单浮层),但**功能完全达成**"单入口 + 内容归代码管"。
- 折中即产品设想 B 本身:后台 1 项 → 代码主菜单卡 → 卡片逐级展开。**可行、推荐。**

## Q4:A vs B 对比
| 维度 | A 后台配多静态项(行情 / 持仓 / 下单各一项) | B 后台配 1 入口 → 代码返主菜单卡 ⭐ |
|---|---|---|
| 飞书支持 | ✅ | ✅(因我们是自建应用) |
| 改菜单(增项 / 改名 / 调序) | 登后台改 + 创版本发布 + 等 5min | **只改 `build_main_menu` 代码 + 发版**,后台一次性 |
| 菜单内容归属 | 散在飞书后台 | **全在代码**(目标达成) |
| 点击层级 | 1 跳直达功能 | 2 跳(点菜单 → 出卡 → 点按钮) |
| 代码改动 | 零(event_key = 各 action) | 零(event_key = `menu:main`) |
| 推荐 | 备选 | **首选**(符合"菜单内容归代码管") |

A 唯一略优:少一跳。但 B 的"代码管内容"灵活性远超这一跳成本,且主菜单卡一次展示全部功能 +
后续按钮逐级展开(下单二次确认等都在卡里)。

## 建议
**采用 B**:飞书后台只配 1 个「📋 菜单 → 推送事件 → event_key=`menu:main`」,**代码零改动**。
本方案**取代**之前 `feishu-bot-menu-setup.md` 的"配 4 个静态项"(那个降级为 A 备选)。
等产品负责人拍板 B → 落地就是"后台配 1 项 + 真机验"(无需改代码,除非顺带美化主菜单卡文案 #295)。

> 备注:还有个更 hack 的等价做法 —— 菜单项动作选「发送文字消息」、文案设成 `/menu`,点击会发一条 `/menu`
> 文本 → 走我们 `im.message.receive_v1` 文本路径 → 同样弹主菜单。但会在会话里留一个 `/menu` 文字气泡,
> 不如「推送事件 + event_key=menu:main」干净。**推荐用推送事件。**
