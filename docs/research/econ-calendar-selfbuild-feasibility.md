# 事件日程提醒层:官方公开源自建可行性调研(build vs buy)

> 状态:**纯调研 · 不碰生产代码 · 未接任何源 · 未注册/申请任何 key · 待 Hans 拍板**
> 方法:40 个并行调研/实测 agent,每个声称的机读 feed 都**真实 curl 打开验证**(不信文档信实测);
> confidence 三档纪律:verified=亲眼见到内容 / claimed=文档说有没打开 / guessed=推测。

## ② 机读性 + 维护负担判定(build vs buy 胜负手)

**实测揭示的真相:前瞻日历几乎没有官方 iCal/RSS**——各央行/统计局的 RSS 全是「已发布新闻」流(9 个 RSS 逐一实测,全部 future=False)。但这**不判自建死刑**,因为:

1. **两个零门槛官方 JSON 覆盖了美国大头**:Fed calendar.json(FOMC 全部+未来半年)+ BEA release_dates.json(GDP 系)——**都已实测拿到真实未来日程,零 key 零反爬**。
2. **中国侧「规则+年表」结构**:LPR 是纯规则(零抓取);统计局是**一年一张精确到时刻的表**——每年 12 月抓一次+每月核对,这不是「爬虫维护负债」量级,是「年度策展」量级。
3. **欧日是年 8 次的硬编码量级**:ECB 提前 2.5 年、BOJ 提前 1 年公布,一年变一次 → **策展年表+低频核对**,与 Midas 现有 `market_calendar.py` 硬编码节假日**完全同构**(已有先例模式)。
4. ★**日程数据的失效模式是良性的**(与价格数据本质不同):价格断供立刻 stale;日程提前 6-30 个月已知,**源断了存量未来日程还能撑数周-数月,有充足修复窗口**。爬虫脆弱性对日程层的杀伤力被结构性削弱。
5. **需要爬 HTML 的只有 3 处,且全部低频**:统计局年表(年 1+月 1 核对)、ECB(月 1)、BOJ(季 1+每年 7 月末)。没有任何高频爬虫。

**唯一的硬骨头是 BLS(非农/CPI 日期)**,三条路(按推荐序):
- a) **香港 VPS + 联系邮箱 UA 拉 bls.ics**(BLS 官方对 UA 的要求即「标识联系方式」;实测该 UA 曾成功拿到 313 个 VEVENT)+ 失败则优雅降级到 b;
- b) **年度种子**:BLS 全年日程头年 10 月公布,非农+CPI 一年就 25 个日期 → 年度策展进种子文件(与 ECB/BOJ 同构);
- c) FRED API(免费 key,单端点覆盖美国全部 release)——最优雅但有两个待验项:香港 VPS 连通性(大陆被 GFW 阻断已实测,HK 未测)+ 需 Hans 注册免费 key。

**维护负担总账(自建)**:2 个每日 JSON 拉取 + 3 个低频 HTML 解析 + 1 个纯规则生成器 + 2-3 张年度策展种子表。**估算稳态维护 ≈ 每年几小时**(年表换届+偶发改版修复)。

## ⑤ 最小自建方案

### 5.1 模块(仿现有 data_sources 结构)

```
apps/api/app/services/data_sources/econ_calendar/
  ├── fed_source.py        # calendar.json 拉取+过滤 FOMC(HTML 页为后备)
  ├── bea_source.py        # release_dates.json
  ├── bls_source.py        # bls.ics(联系邮箱 UA)→ 失败降级种子
  ├── stats_cn_source.py   # 统计局年表 HTML 解析(年 1+月 1)
  ├── rule_source.py       # LPR 规则生成器 + 社融/M2 窗口占位(零网络)
  └── seed.py              # 策展种子:ECB/BOJ 年表 + BLS 兜底年表
                           #(与 market_calendar.py 硬编码节假日同构·年度更新)
```

### 5.2 存储:**建议 PG 单表,不用 CH**(自主决策,可 override)

事件是**可变实体**(改期要 UPDATE、按 event_key 幂等 upsert),年增量仅 ~150 行——这是 PG 的场景,CH(append 型分析库)反而别扭。

```sql
econ_event(
  event_key      TEXT PRIMARY KEY,   -- 如 "fomc-2026-12-15" / "cn-cpi-2026-08"
  event_type     TEXT,               -- fomc / us_cpi / nfp / cn_gdp / lpr / ...
  title          TEXT,
  markets        TEXT[],             -- ['us','crypto'] / ['cn','hk']
  importance     SMALLINT,           -- 3/2/1
  scheduled_at   TIMESTAMPTZ,        -- ★tz-aware(项目铁律);Fed 无时区标注需 America/New_York 换算,统计局 Asia/Shanghai
  time_confirmed BOOLEAN,            -- false=窗口占位(社融/M2)
  source         TEXT,               -- fed_json / bea_json / bls_ics / stats_cn / rule / seed
  updated_at     TIMESTAMPTZ
)
```

### 5.3 Celery beat(3 个低频任务)

| 任务 | 频率 | 干什么 |
|---|---|---|
| `econ_calendar_us_refresh` | 每日 1 次 | Fed JSON + BEA JSON + BLS ics,upsert diff |
| `econ_calendar_cn_refresh` | 每周 1 次(12 月加密到每日) | 统计局年表解析 + LPR/社融规则生成未来 12 个月 |
| `econ_calendar_seed_check` | 每月 1 次 | ECB/BOJ 页面核对种子表,漂移→TG 告警 admin 提醒更新种子 |

### 5.4 决策卡注入(复用上一轮金十调研 §5.3 的同一挂点)

`_node_data_prepare` → `_format_snapshot` 增加一段事件背景:该品种 `markets` 匹配的**未来 7 天 importance≥2 事件**(如「7/15 10:00 中国二季度 GDP · 7/29 FOMC 决议」)。★格式:只陈述事件与时间+标注来源,**不做因果预测**(契合 prompt 机器证明红线);未来可点亮 `AgentScore` 已预留的宏观维度。

### 5.5 保鲜(★last-run,不是 max(ts))

事件 ts 在未来,`max(scheduled_at)` 永远「新鲜」——**监控口径必须是采集任务 last-run 成功时间**:
- 每个 source 任务成功后写 `econ_calendar_last_success:{source}`(Redis 或 PG 小表);
- **`ingest_monitor.py` 加一类 job-freshness 检查**(现有范式扩一类):`last_success` 超过阈值(us 源 3 天/cn 源 15 天/seed 45 天)→ TG 告警;
- ★降级策略利用日程数据的良性失效:stale 后**存量未来日程继续可用**(它们仍然有效),仅在决策卡 context 附「日程截至 X 日」;超过 30 天才降级为「事件面暂不可用」占位——**绝不因源断了就丢掉手里仍有效的日程**。

### 5.6 分阶段

- **P0(零外部依赖即可跑)**:rule_source(LPR/社融窗口)+ seed(ECB/BOJ/FOMC 手工录当年表)+ 统计局年表解析 → 已覆盖最小集 80%,**零 key 零反爬风险**。
- **P1**:Fed JSON + BEA JSON 每日任务(已实测零门槛)+ BLS ics(香港 VPS 实测 UA 策略)。
- **P2(可选加固)**:Hans 注册免费 FRED key + 香港 VPS 连通性验证 → 美国日程整体切 FRED 单源,BLS/种子降为对照。

## ⑥ 一句话结论

**自建可行且真·低维护,不是硬凑**:美国大头有两个已实测的零门槛官方 JSON(Fed calendar.json + BEA release_dates.json),中国侧 LPR 是纯规则、统计局是一年一张精确到时刻的年表,欧日是年 8 次的硬编码量级(与现有 market_calendar.py 节假日模式同构),唯一硬骨头 BLS 有「合规 UA + 年度种子」双保险,且日程数据失效模式良性(提前数月已知,源断了存量仍有效)——稳态维护每年几小时,对比金十 2000 元/年/板块且其日历板块同样只解决日程不解决注入。**建议:走自建 P0→P1;金十留作二期「实时快讯+实际值」需求出现时再评估买**(那才是它的不可替代区,见上一轮金十调研)。
